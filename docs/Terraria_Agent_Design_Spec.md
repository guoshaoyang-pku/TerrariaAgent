## 1. 项目目标与推进顺序

### 1.1 总体目标

构建能够长时间自主推进 Terraria 游戏流程的 Agent。大模型处理阶段目标、策略、装备与资源安排，并在需要时编写或修改程序；具体跑图、走位、采矿、合成、建造和高频避险交给脚本及搜索控制。

系统应在实际游戏过程中不断试验、修正和积累脚本。期望通过多局经验，逐渐具备接近熟练速通玩家的临场处理能力。

### 1.2 先完成一个完整流程

初期使用一个新取得的随机种子，固定下来进行开发和反复试验。这里的“固定”指同一世界可重复运行；用户明确不希望依赖公认特别有利的“绝世好种”。

先把正常流程完整走齐，并打通讨论范围内的全部 Boss。不能仅以一个孤立的移动、采矿或 Boss 演示代替这个最终目标。

“全部 Boss”的具体清单、是否包含事件 Boss、特殊世界内容或 Mod Boss 尚未确定，需要结合选用的游戏版本列明。本文件不自行把目标缩成只击败某一个终局 Boss。

### 1.3 后续适配多个地图

在一个固定随机世界中打磨工具后，再适配多个地图和种子。应逐步使通用脚本和策略能够处理不同地形及不同局面。

用户提出由已经可观测的地图部分推断地图，而不是直接通过种子判断整张地图。该方向需保留，具体可观测范围见第 4 节。

### 1.4 效率目标

除了完成流程，还希望：

- 跑图尽可能快，且能处理沿途敌怪。
- 探索时有效取得宝箱和所需资源。
- 战斗以无伤为目标，并在此前提下尽量提高输出。
- 采矿、建造和合成由程序有效执行。
- 随着多次试验减少重复失败，积累可复用的脚本。

初次通关的耗时上限、死亡上限、成功率门槛和预算均未确定。“先完成流程”和“后续提高速度、稳定性与泛化能力”应保留为不同阶段。

来源：H1、H2、H3。

## 2. 游戏运行与实验边界

### 2.1 已明确允许的做法

- 在决策点暂停游戏，让大模型思考、写代码或修改脚本。
- SL，即保存／读取与重复尝试；允许回滚。
- 从当前状态进行分叉探索。
- 使用多个 Agent。
- 为不同 Boss 准备专门脚本。
- 在运行中不断完善和沉淀脚本。
- 借鉴现有辅助脚本、游戏规则和速通经验。

这些是本项目允许的开发与运行手段，不应被擅自改成“不暂停、不读档、单次运行、纯视觉”的限制。

### 2.2 尚未确定的运行设置

| 设置 | 讨论状态 |
| --- | --- |
| Terraria 版本与具体构建 | 待定 |
| 原版还是带 Mod；采用何种接口 | 待定 |
| 世界大小、难度、人物难度 | 待定 |
| 单机或服务器环境 | 待定 |
| 同时运行的游戏角色和游戏实例数 | 待定 |
| 存档回滚能否恢复到帧级状态 | 待定 |
| 暂停与恢复的具体实现 | 待定 |
| 是否加速模拟，以及游戏时钟与墙钟时间如何区分 | 待定 |
| 内部状态读取的可见范围 | 待定，不能由“可读游戏状态”直接推成全图公开 |
| 调试用状态修改与正式流程的边界 | 待定；“正常流程”目标已明确 |

来源：H1、H2、H5。

## 3. 上层、中层与下层的职责

### 3.1 职责总表

| 层级 | 负责的问题 | 讨论中的具体例子 |
| --- | --- | --- |
| 上层大模型 | 现在做什么、为什么做、准备是否充分 | 流程阶段、路线方向、Boss 策略、配装、资源与金钱管理、要采哪些矿脉、要不要坐矿车 |
| 中层 | 把较大目标整理成可执行的小目标，并辅助判断和比较 | 路线分段、关键点、对象或区域 Mask、候选方案评估 |
| 下层脚本与控制程序 | 如何连续、快速、正确地执行 | 跑图、走位、局部搜索、挖掘、投放炸弹、采集、合成、建房、陷阱和岩浆避险 |

这里区分的是职责，不要求每一层必须由一个独立模型实现。底层也不必是神经网络；用户反复强调早期以脚本为主。

### 3.2 上层大模型

上层需要掌握当前流程与资源情况，并作出具有较长影响的决策：

1. 当前要推进哪个阶段、哪个目标。
2. 是否已经具备挑战目标 Boss 的条件。
3. 当前装备、武器和物资是否合适。
4. 钱要怎么攒，物资如何安排。
5. 已发现的资源中，哪些值得或需要采集。
6. 是否使用遇到的矿车轨道。
7. 原有脚本不足时，是否暂停并修改脚本。

上层需要给装备把关。底层执行得快，不能替代对装备与流程需求的判断。

### 3.3 中层

用户讨论过小专家模型、视觉／对象模型等可能性，也强调精细专家模型的训练比较复杂。

中层可承担路线分段、对象或区域表达、关键点安排等工作。流程中还可以使用一个快速模型判断和比较候选方案，语音转录将其写作“JEFF”，具体名称待核对。

“快速比较模型”和完整中层模型是否为同一模型，没有确定。本文件不将二者强行合并为一个固定模块。

### 3.4 早期允许上中层由同一大模型承担

用户明确允许早期把上层和中层的任务都交给上层大模型。原因是训练独立模型较复杂，应先把流程做起来。

这意味着：职责仍然存在，但可以由同一模型给出阶段目标、分段目标及必要判断。下层的具体连续动作仍由脚本与控制程序执行。

不能把“必须先训练中层模型”设为开始实现的前置条件。

### 3.5 下层

下层承担高频决策和执行，包括根据当前地形与危险调整动作。下层不是只把坐标转换为按键；还要处理到达目标、敌怪干扰、地形修改、爆炸风险和即时操作。

各层的调用频率、进程结构、消息格式和控制权切换协议尚未确定。

来源：H2、H3、H4、U3、U4、U6、U8。

## 4. 游戏状态、地图与可观测范围

### 4.1 利用游戏已有信息

用户允许利用游戏内部已有的信息提取对象与位置，用筛选、滤镜或标注方式形成模型可理解的输入。

对矿脉、宝箱等已经可识别的对象，可以直接获取位置和范围。为此不必先使用 SAM 等通用图像分割模型。

该讨论并没有确定一套具体的状态读取 Mod、内存接口或服务端协议。tModLoader、TShock 等仅是助手提出的参考方向，见附录 A、B。

### 4.2 内部数据来源与允许观察的范围分别确定

“使用游戏内部信息”说明数据可以如何获取；“Agent 允许看见哪些信息”仍需在运行设置中明确。

用户已经提出后续基于可观测部分推断地图、不直接通过种子判断整张地图。实现不能仅凭底层能够读取某个字段，就声称用户已经允许上层直接看到全部未探索内容。

初期是否允许全图辅助开发、未探索方块如何遮挡、可见区域如何随探索更新，本次没有确定。

### 4.3 已表达的状态需求

按讨论涉及的任务，状态输入需要能够支持以下判断：

- 角色当前位置及所在局面。
- 当前地形与可走路线。
- 已发现的矿脉、宝箱和相应位置。
- 敌怪、陷阱、岩浆等与当前执行相关的危险。
- 当前装备、金钱和流程所需资源。
- 当前游戏阶段及已完成的流程目标。

以上列的是任务所需信息，不是已经确定的字段表。数据格式、更新频率与可见性由实现继续细化。

来源：H1、H2、H3、U4、U6、U8。

## 5. 给上层模型看的地图与对象表示

### 5.1 本次问题明确针对上层

用户特意纠正过：讨论“给视觉画面还是对象坐标”时，问的是上层模型的输入。

不能仅回答中下层应该读取精确状态，就遗漏上层如何理解场景、识别目标和作出选择。

### 5.2 讨论过的输入形式

| 形式 | 已讨论的用法 | 是否已确定为唯一形式 |
| --- | --- | --- |
| 游戏视觉画面 | 帮助理解具体地形和场景 | 否 |
| 加滤镜／标注的画面 | 筛选对象，在对象附近放数字 | 否 |
| 对象坐标 | 直接把位置提示给上层 | 否 |
| 对象编号及概要 | 上层按编号选目标，降低精确坐标描述负担 | 是明确提出的接口方向，但最终展示格式待定 |
| Mask 或精确坐标集合 | 将所选对象准确传给执行程序 | 是明确提出的表达方向，编码形式待定 |

没有决定每次必须同时提供截图、标注图和对象表，也没有决定必须纯视觉或必须纯结构化输入。

### 5.3 宝箱

用户举例：将宝箱标成宝箱 1、宝箱 2、宝箱 3、宝箱 4。上层通过编号对应到具体目标。

可以在画面上标号，也可以直接给出其坐标。编号与坐标之间需要有明确对应关系，具体实现未指定。

### 5.4 矿脉

对已经发现的每个矿脉，向上层提供：

1. 可引用的编号。
2. 靠近该矿脉质心的一个代表坐标。
3. 该矿脉包含多少矿。
4. 与其对应的精确范围，供下层通过 Mask 或坐标集合使用。

用户的设计重点是：上层决定“开采哪些编号的矿脉”，不必逐块列出所有矿石的位置。

“质心附近坐标”用于指代矿脉。它与角色实际能够站立、接近或投放炸弹的位置不是同一个已定义的量；具体接近和操作位置由下层搜索处理。

### 5.5 尚未确定的细节

- 矿脉的分组和连通规则。
- “多少矿”的单位及统计范围。
- 编号是否跨多次观测保持不变。
- 矿脉被部分挖掉或完全挖空后如何更新编号。
- 世界坐标、格子坐标与屏幕坐标如何对应。
- Mask 的编码和精度。
- 视觉图与对象表分别在什么情况下提供。

来源：U8。

## 6. 从上层目标到下层执行

### 6.1 已明确的信息流

1. 系统取得当前允许使用的地图与对象信息。
2. 对已发现的资源进行编号和必要标注。
3. 上层根据当前流程需求，选择需要采集的对象。
4. 将所选编号对应的范围或精确坐标交给下层。
5. 下层规划并执行移动、挖掘、爆破等操作。
6. 继续依据实际资源缺口决定是否寻找更多资源。

上述顺序是在同一处展开用户已讨论的关系，不限定软件调用栈或必须采用某种 RPC。

### 6.2 各类决策的分工

| 任务 | 上层决策 | 下层工作 |
| --- | --- | --- |
| 采矿 | 需要什么资源、选哪些矿脉 | 到达、选择具体操作位置、挖掘／爆破、处理危险 |
| 探索 | 当前要探索哪里、推进什么目标 | 路线搜索、局部走位、开路、应对敌怪 |
| 矿车 | 是否乘坐 | 乘车操作、识别危险后的跳跃或停车 |
| Boss | 是否挑战、总体打法、配装准备 | 具体移动、攻击和躲避 |
| 合成 | 流程需要的物品与准备 | 脚本完成合成操作 |
| 建房 | 目标、规则、候选方案的取舍 | 搜索候选方案并执行建造 |

### 6.3 不过早固化接口

本次确定的是语义关系。任务名称、请求字段、返回结构、错误码、取消方式等还没有讨论。

尤其需要后续明确：上层指定“把这些矿脉全部挖完”后，如果中途已经满足资源阈值，是否允许提前停止。用户同时谈到了完成已选目标和补足流程需求，但没有给出两者冲突时的优先级。

来源：H2、H3、U1、U3、U4、U6、U8。

## 7. 跑图、探索与局部避怪

### 7.1 连续跑图

用户希望从一个位置到另一个位置时，脚本能尽可能快地移动，并能够处理途中遇到的怪物。

讨论还提到雨中和沙暴情况下的跑图，因此控制器不能只围绕一个无天气变化、没有干扰的场景成立。此处保留场景要求，不指定天气模型或控制策略。

### 7.2 丛林探索例子

用户举出的具体任务是：用 MPC 规划较快的丛林探索路径，尽量取得更多宝箱，并允许用雷管、炸弹和镐开路。

这说明探索路线不能只考虑已有空隙中的移动。需要同时考虑是否通过挖掘或爆破改变可通行区域，以及这些操作花费的时间。

“尽可能多宝箱”与“尽可能快”如何折中，尚无固定目标函数。

### 7.3 早期避怪假设

用户提出过一个早期简化：先假设可以通过小幅走位躲开所有怪物，再在此基础上研究 MPC 与路线控制。

这是一项允许先试的假设，不是对任意地形、装备和敌怪组合的保证。实现需要检验这个假设在哪些场景有效，不能把它直接当作环境事实。

### 7.4 敌怪对路线的影响

用户明确要求搜索考虑敌怪动作，以及骚扰造成的时间浪费。路线代价不能只反映静态地形上的距离。

远距离路径需要适当的启发式与路线分割；敌怪走位需要在局部控制中处理。具体启发式、局部范围和重新规划条件没有确定。

来源：H2、H3、H4。

## 8. MPC、游戏内核与战斗

### 8.1 利用游戏内核做预测和控制

用户提出：“有游戏内核的时候，我们可以直接做 MPC。”核心意图是利用游戏状态和演化机制，预测接下来可能出现的局面并搜索动作。

其中一个重要例子是预测 Boss 弹幕，再规划走位躲避。

这表达了使用游戏机制进行前向预测的方向。尚未确定如何提取或调用游戏逻辑，是否使用完整游戏步进、局部模拟或近似模型，也未确定预测可以可靠覆盖多长时间。

### 8.2 战斗职责

上层决定要不要打、何时打、总体打法及准备情况。底层负责实际移动、走位、攻击与躲避。

用户允许每个 Boss 有自己的专门脚本，并希望通过多次运行积累临场处理经验。具体脚本结构没有确定。

### 8.3 战斗目标

用户提出无伤前提下尽可能高输出。该目标应体现在搜索、脚本设计与后续评估中。

没有给出允许受伤阈值，也没有确定“无法找到无伤动作”时如何取舍。此时的策略是待定项，不在本文件中补成主动换血或固定撤退规则。

### 8.4 预测的边界

敌怪状态会随玩家过去的动作改变。用户已经注意到：把这样的完整历史都纳入搜索，会使状态规模失控。

因此，需要把预测精度、搜索范围和实际计算时间一并考虑。游戏机制可读，并不自动意味着所有未来弹幕和敌怪行为都可以无误差预知。

随机数状态、隐藏状态、模拟与真实执行的一致性，以及预测失败时如何处理，本次均没有给出具体实现。

来源：H2、H3、H4。

## 9. 搜索分段、状态压缩与计算延迟

### 9.1 程序需要考虑计算延迟

用户明确提出程序要 latency-aware，并解释为让计算与程序运行速度匹配，能够较快完成搜索。

因此，算法不仅要能找到好方案，还要在实际机器提供的计算时间内得到可用结果。允许上层暂停思考，并不消除底层连续执行时的计算需求。

具体每次搜索可用多少毫秒、模型调用可等待多久、是否并行计算，都没有确定。

### 9.2 适当分割长路线

用户指出，起点和终点距离过远时，中间状态可能迅速膨胀。中层或上层应对路线作适当分割。

需要避免把远距离地形、玩家动作历史、敌怪变化和所有挖掘结果无界地组合在一个搜索问题里。分割的位置、每段长度及各段如何衔接，留给实施阶段设计。

### 9.3 空间近似

用户讨论过把玩家高度等空间状态近似到若干格子／槽位，以减少状态数量。

历史摘要还保留了“距离的 n²”“格子顶多几百乘几百”等估计。这些只记作对局部近似和搜索规模的直觉，不表示已经证明算法为 O(n²)，也不表示整张 Terraria 世界只有这个尺寸。

具体如何离散化位置、速度、跳跃阶段或碰撞状态，没有确定。

### 9.4 地形变化与状态表示

挖掘和炸弹会改变世界状态。用户提出这些变化需要设法压缩，某些状态可能需要用 hash 存储。

这是对状态表示与搜索开销的要求。没有确定哈希键包含哪些字段、是否存地形差分、如何处理碰撞或怎样复用搜索结果。

### 9.5 不把实现选择写成已定算法

本次没有选定 A*、MCTS、束搜索、动态规划、集合覆盖或路线组合算法，也没有确定 MPC 的预测步数、控制步长和滚动频率。

用户明确的是：分段、近似、压缩，避免状态爆炸，并让搜索在实际算力下运行得足够快。

来源：H3、H4、U5。

## 12. 爆破采矿的分块与执行

### 12.1 避免遍历所有炸弹位置

用户明确反对直接暴力搜索“炸弹可以放在每一个点”的所有组合。

应先按地形或拓扑把问题拆成若干部分，再处理每部分的爆破覆盖和手工开采。具体分块算法未确定。

### 12.2 需要解决的内容

1. 每颗炸弹计划覆盖哪些区域。
2. 哪些矿石或地形由炸弹处理。
3. 哪些剩余部分用镐挖。
4. 使用何种炸弹及大致数量。
5. 角色如何到达对应操作位置。
6. 如何较快完成投放和后续手工操作。
7. 如何避免角色被自己的炸弹炸死。

分块不仅是把地图裁成几张图；它要帮助减少爆破与挖掘组合的搜索规模。

### 12.3 成本考虑

用户提出可给炸弹数量及其他消耗赋予权重，尝试减少耗材；也讨论了人物到达投放位置所需的时间。

相应规划至少要面对以下取舍：

- 更多爆炸物是否换来更短的开采时间。
- 更少爆炸物是否导致更长的走路或手挖时间。
- 理论覆盖更好的投放点是否难以到达。
- 敌怪干扰是否增加实际执行时间。

这里没有固定的加权公式。语音中“没把……算进去”与下一句“所需的时间算进去”存在局部转录冲突；按连续语义保留“讨论将人物到达位置所需时间计入成本”，不擅自确定数值权重。

### 12.4 安全目标

用户明确要求不能被自己的炸弹炸死。这是爆破执行的约束，需要与到位、投放和后续移动共同考虑。

具体引信、撤离距离、是否允许同时投多颗炸弹、如何安排等待和避险，本次未确定。实现必须使用实际游戏规则，不能凭代表坐标就直接投放。

### 12.5 复杂度预期

用户希望通过分块，使计算复杂度接近直接跑图路径搜索的量级。

这是待验证的设计预期。本文不保证分块后得到全局最优解，不保证相邻块之间相互独立，也不把该预期写成已证明的复杂度上界。

## 18. 借鉴已有工具与判断封装程度

### 18.1 用户希望借鉴现成脚本

用户提出可以研究 Minecraft 或 Terraria 现有辅助脚本，尤其是自动采矿一类，即使它们比较简单，也可能提供可复用的规则或实现思路。

### 18.2 不能只看“模型通关”的标题

用户关心一个通关系统实际替模型完成了多少工作。若底层已经封装了大量路径、采矿或流程逻辑，仅说模型做了几个高层决策，不足以说明它具备本项目所需的复杂场景处理能力。

因此，研究参考系统时，需要弄清：

- 输入是图像，还是直接提供对象、方块、坐标和背包。
- 接口提供基本动作，还是完整采矿／寻路任务。
- 路线、战斗和流程代码由人编写，还是由 Agent 在运行中生成。
- 运行时是否有人修复、指挥或干预。
- 使用多少个游戏 Agent，是否在同一个世界／种子里。
- 种子是随机生成、固定挑选，还是预先探索过。
- 实际完成耗时、工作日期和成功次数。

这些是讨论中提出的核查问题，不代表拒绝使用强脚本。项目本身明确希望下层脚本强大；关键是准确说明每一部分承担了什么。

| 观察表示 | 图像、标注图、对象表如何组合 | 上层按编号选择是明确方向 |
| 对象分组 | 矿脉连通、矿量单位、编号更新 | 需要编号、代表坐标、矿量与精确范围对应 |
| 坐标／Mask | 坐标系、单位、Mask 编码 | 下层需要能定位到真实对象范围 |
| 搜索 | 分段规则、启发式、搜索算法 | 必须重视实际计算时间与状态规模 |
| 状态压缩 | 格子／槽位精度、hash 内容、地形变化表示 | 用户提出近似、压缩和可能使用 hash |
| MPC | 预测时域、控制周期、模拟实现与误差 | 用游戏内核预测、搜索动作的方向已提出 |
| 敌怪预测 | 如何处理动作历史、随机性和预测失准 | 不能只按静态地图规划 |
| 资源 | 阈值、库存范围、资金目标、任务优先级 | 不足则继续寻找并补齐 |
| 采集结束 | 阈值满足时是否中断已选矿脉 | 目前存在两种结束语义，需要细化 |
| 采矿规则 | 镐、矿石、力量炸弹的确切 ID 和配方 | 口述先验保留，机制须结合实际版本核对 |
| 爆破 | 分块方法、成本权重、投放与撤离动作 | 同时考虑覆盖、耗材、移动时间与自伤风险 |
| 矿车 | 识别距离、跳跃时机、制动条件 | 依危险选择操作，不假设备用轨道 |
| 建房 | 规则、候选数量、评分和保留方式 | 可以保留稍慢但不挡路的方案 |
| 模型 | 主力品牌、版本、“JEFF”“Tera”的准确含义 | 早期可以上中层合并 |
| SL | 存档粒度、保存点、恢复状态范围 | 允许 SL 与回滚 |
| 分叉 | 并发数、世界／角色安排、分支选择 | 允许 fork；知识／脚本与游戏状态应区分 |
| 经验积累 | 保存哪些经验、脚本如何管理和复用 | 需要持续积累，但实现方式未定 |
| 指标 | 通关耗时、算力预算、成功率及评估种子数 | 本次没有给出硬数值 |

## 21. 对实现结果的需求核对清单

本节仅将前文要求转成检查项，不新增测试阈值或实施任务。

### 21.1 架构与流程

- [ ] 保留完整流程与全 Boss 的目标，并明确实际 Boss 清单。
- [ ] 从新的随机固定种子起步，后续能够向多个地图扩展。
- [ ] 上层负责目标、配装、金钱与物资安排。
- [ ] 早期可由同一大模型承担上层和中层。
- [ ] 连续移动、走位和即时危险处理由下层执行。
- [ ] 允许在决策点暂停、改脚本、SL 和分叉试验。

### 21.2 地图与目标选择

- [ ] 上层能够理解当前场景及已发现的目标。
- [ ] 宝箱、矿脉等对象可用编号明确引用。
- [ ] 矿脉有代表坐标、矿量与精确范围的对应。
- [ ] 上层选定的编号能准确映射到执行对象。
- [ ] 将观察范围和内部读取能力分开说明。

### 21.3 搜索、资源与爆破

- [ ] 路线搜索考虑敌怪动作及干扰耗时。
- [ ] 长路线和爆破问题采取适当分段／分块。
- [ ] 搜索关注实际延迟，地形变化状态不会被忽略。
- [ ] 资源不足时继续寻找，并与当前流程需求对应。
- [ ] 爆破与镐挖能够共同规划。
- [ ] 规划考虑耗材和到达操作位置所需时间。
- [ ] 爆破执行包含避免自炸死亡的处理。
- [ ] 复杂度预期以实验或分析验证，不直接宣称已证明。

### 21.4 具体任务

- [ ] 跑图能面对沿途怪物，并覆盖讨论中的天气场景。
- [ ] Boss 控制体现躲避与输出目标，并允许专门脚本。
- [ ] 矿车是否乘坐由上层决定，跳跃与停车由下层及时处理。
- [ ] 不将自然轨道视为一定存在备用路线的网络。
- [ ] 合成与建房通过脚本执行。
- [ ] 建房候选方案能保留“不挡路”等用户明确提到的价值。
- [ ] 失败和重复运行能够用于改进、积累脚本。

### 21.5 需求忠实性

- [ ] 助手建议没有被混写成用户已确认的设计。
- [ ] 模糊转录没有直接变成物品 ID、配方或模型版本。
- [ ] 未讨论的参数有明确标记，未伪装成用户决定。

## 附录 B. 外部参考与必要的事实澄清

核对日期：2026-10-28。这里只澄清对话中已提到的资料，不扩展成新的选型或文献综述。

### B.1 Mineflayer 的功能边界

| 项目 | 官方资料支持的能力 | 参考 |
| --- | --- | --- |
| Mineflayer 核心 | 读取方块、实体、背包等状态；提供移动控制、挖指定方块、放置、攻击及按配方合成等 API | [核心 API 文档](https://github.com/PrismarineJS/mineflayer/blob/master/docs/api.md) |
| mineflayer-pathfinder | 到目标位置的寻路；可定制移动与代价，途中破坏／放置方块，随环境变化更新路径 | [官方仓库](https://github.com/PrismarineJS/mineflayer-pathfinder) |
| mineflayer-collectblock | 将寻路、选工具、挖掘与收集掉落包装为采集调用；使用 pathfinder、tool 等插件 | [官方仓库](https://github.com/PrismarineJS/mineflayer-collectblock) |

因此，对话里“Mineflayer 直接自动找路、自动挖矿”的说法需要具体区分核心 API、插件和系统自己编写的逻辑。读取对象状态也不等于完全不用处理敌怪或复杂场景。

### B.2 对话中的 Gemini Minecraft 论文

[论文摘要](https://arxiv.org/abs/2610.22319)与[全文](https://arxiv.org/html/2610.22319v1)报告：论文于 2026-10-15 提交；4 个 Gemini 4 Argon 游戏 Agent 在同一个随机生成的 Easy 世界协作，27 小时 14 分钟击败末影龙，累计死亡 605 次，获胜前编写 2,783 个程序。

全文明确使用 Mineflayer，并预先加载 pathfinding 插件；报告只覆盖一次运行，不能据此给出稳定成功率。另有观察 Agent，不控制游戏玩家。以上是论文报告，不是本项目对其进行的独立复现。

这里保留人数、同一世界、时长、日期及封装条件，是为了回应用户在讨论中提出的核查问题，不据此确定 Terraria 的 Agent 数量或目标耗时。

### B.3 Superbloom Steve

[项目方介绍](https://superbloom.gg/steve-1.html)报告：在 100 个随机种子、Normal 难度的运行中成功 90 次，平均耗时 46 小时；使用 Mineflayer，路径库已安装但初始未加载，可由 Agent 自行加载。该页也描述了 Agent 自行编写、测试和改善程序的方式。

上述成功率和时间属于项目方报告，本次没有独立验证。其执行模型名写作 Jev，不能仅凭读音就确认用户语音中的“JEFF”一定指它。
